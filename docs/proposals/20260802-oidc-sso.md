# 20260802-oidc-sso.md

Proposal: Migration from Email/Password Authentication to OIDC SSO

This document proposes replacing the current private email/password authentication system with an OpenID Connect (OIDC) Single Sign‑On (SSO) model. It describes the limitations of the existing approach, the benefits of OIDC, expected architectural changes, and the migration plan for biolineage.

---

## 1. Overview

biolineage currently uses a private email/password login mechanism. This system is functional but limited, and does not align with modern authentication standards. OIDC SSO provides a secure, standardized, and maintainable alternative.

This proposal outlines the intent to migrate to OIDC SSO in a future milestone. It does not represent completed work.

---

## 2. Limitations of the Current Authentication Model

The existing email/password system has several constraints:

- passwords must be stored, hashed, and managed
- password resets require manual handling
- no multi‑factor authentication
- no federated identity support
- no session revocation or centralized identity control
- limited auditability
- not suitable for future multi‑instance deployments

While acceptable for early development, it is not ideal for long‑term operation.

---

## 3. Benefits of OIDC SSO

Migrating to OIDC SSO provides:

- secure, standards‑based authentication
- no password storage in biolineage
- support for multi‑factor authentication
- centralized identity management
- compatibility with Azure AD, Auth0, Keycloak, and other providers
- easier user provisioning and deprovisioning
- improved audit logging
- future compatibility with additional frontend components
- simplified session handling via Redis

OIDC is widely supported and aligns with modern best practices.

---

## 4. Candidate Identity Providers

Several OIDC providers are under consideration:

- Azure Active Directory
- Auth0
- Keycloak
- Okta
- self‑hosted OIDC providers

The final choice will depend on cost, ease of integration, and long‑term maintainability.

---

## 5. Expected Backend Changes

Migrating to OIDC will require updates to the backend:

- add OIDC client configuration to the Fastify server
- replace email/password login routes with OIDC redirect endpoints
- validate ID tokens and user claims
- store session identifiers in Redis
- remove password hashing and storage logic
- update user table to store OIDC subject identifiers
- add logout and session revocation endpoints

These changes will be implemented in a future milestone.

---

## 6. Expected Frontend Changes

Frontend authentication will shift from:

- manual login forms
- password fields
- local session cookies

to:

- OIDC login redirects
- provider‑managed authentication screens
- standardized callback handling
- token‑based session initialization

The frontend will not store passwords or handle password resets.

---

## 7. Session Storage

Redis will serve as the session store for OIDC:

- stores session tokens
- supports expiration and revocation
- integrates cleanly with Fastify
- avoids storing session data in PostgreSQL

This improves performance and simplifies authentication logic.

---

## 8. Migration Plan

The migration will occur in phases:

1. introduce OIDC client configuration
2. add login and callback routes
3. implement Redis‑backed session storage
4. migrate user records to OIDC subject identifiers
5. deprecate email/password login
6. remove password storage and hashing logic
7. update frontend to use OIDC redirects
8. finalize documentation and update API references

The existing login system will remain functional until the migration is complete.

---

## 9. Backward Compatibility

During migration:

- both authentication systems may temporarily coexist
- existing users will be mapped to OIDC identities
- no historical data will be affected
- API behavior will remain unchanged

Once OIDC is fully deployed, the email/password system will be removed.

---

## 10. Summary

This proposal describes the planned migration from private email/password authentication to OIDC SSO. The change will improve security, maintainability, and long‑term viability. Implementation will occur in a future milestone and will not affect existing lineage, event, or place data.
